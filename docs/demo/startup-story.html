Chapter 1: Olive unlocks the library
app.py:lifespan

The library has a strict rule: no visitors until the morning routine is finished. Who does the routine, and what's on her list?

📖 Every morning, Opening Olive arrives before anyone else. She grabs the Clipboard (it says where the storeroom is and how many times to knock), gets the storeroom open, and leaves the key on the front desk where every librarian can reach it. 🧩 Lifespan

📖 The story: Olive's "open in the morning, lock up at night" routine. Visitors only come in between.
🔧 What it really is: a FastAPI hook that runs setup code once before the server accepts requests, and cleanup code once when it stops. The yield marks the boundary. app.py:9–17
🎯 Why we need it here: opening a database is slow. We want to do it once and share the connection, not once per request.
💥 What breaks without it: you'd open the database inside every request (slower, and you can hit "too many open files"), or open it at import time, where tests and reloads leave connections dangling and nothing ever calls close().

Olive has the Clipboard. Now she walks to the storeroom… but what if the door is stuck? 🚪

↳ Going deeper: connect_with_retry()
app.py:lifespan → db.py:init_db → db.py:connect_with_retry

📖 Dan knocks. If nobody answers, he doesn't give up right away: he waits a little, knocks again, waits a bit longer, and knocks one last time. Only after the last knock fails does he run back shouting "the storeroom is broken!"

  7  def connect_with_retry(path: str, retries: int) -> sqlite3.Connection:
  8      for attempt in range(1, retries + 1):
  9          try:
 10              conn = sqlite3.connect(path, check_same_thread=False)
 11              conn.execute("SELECT 1")
 12              return conn
 13          except sqlite3.OperationalError:
 14              if attempt == retries:
 15                  raise
 16              time.sleep(0.5 * attempt)
  1. ① line 8: with retries=3, attempt goes 1, 2, 3.
  2. ② line 10: opens the SQLite file (creates it if missing). check_same_thread=False lets the connection be shared, because FastAPI may run requests on different threads.
  3. ③ line 11: a tiny "are you there?" query. Opening the file isn't proof that it works.
  4. ④ line 12: success, so hand back the connection and stop the loop.
  5. ⑤ lines 14–15: on the last attempt, give up and let the error travel up to lifespan. The app refuses to start.
  6. ⑥ line 16: wait 0.5 s after the 1st failure, 1.0 s after the 2nd. The waits get longer each time.
Inpath="notes.db", retries=3Outan open connection, or an OperationalError after 3 failed tries (e.g. the folder doesn't exist or the file is locked)

⬆️ Climbing back up: the connection returns to db.py:29 as conn.

🧩 Retry with backoff

📖 The story: Dan knocks, waits, knocks again, waits longer. He's patient, but not forever.
🔧 What it really is: repeating an operation that can fail temporarily, waiting longer between tries ("backoff"), and giving up after a fixed number of attempts. db.py:7–16
🎯 Why we need it here: in real deployments the database is often a few seconds slower to start than the app, or a file is briefly locked.
💥 What breaks without it: one hiccup at startup crashes the app. In Docker or Kubernetes you'd see the container restart in a loop. With no limit on retries, it would hang forever instead of failing loudly.
↳ Going deeper: create_tables()
app.py:lifespan → db.py:init_db → db.py:create_tables

📖 Sam checks: "Is there a notes shelf? No? I'll build one." Then he does something clever: he makes a name-tag drawer that lists whose notes sit where, so finding someone's notes doesn't mean reading every note on the shelf.

 19  def create_tables(conn: sqlite3.Connection) -> None:
 20      conn.execute(
 21          "CREATE TABLE IF NOT EXISTS notes ("
 22          "id INTEGER PRIMARY KEY, owner TEXT NOT NULL, body TEXT NOT NULL)"
 23      )
 24      conn.execute("CREATE INDEX IF NOT EXISTS idx_notes_owner ON notes(owner)")
 25      conn.commit()
  1. ① lines 20–23: build the notes table only if it doesn't exist, so restarting the app never wipes your data.
  2. ② line 24: build an index on owner. This is the name-tag drawer. ↳ term card
  3. ③ line 25: commit() = "save!" Without it, the changes might not stick.
Inconn: the open connectionOutnothing returned. Side effect: the notes table and idx_notes_owner index exist in the file.

🧩 Database index

📖 The story: a million notes on one long shelf. A visitor asks for "all of Kid's notes." Without the name-tag drawer, Sam reads every single note. With it, he opens the drawer at "K" and walks straight to the right spots.
🔧 What it really is: a separate sorted structure (a B-tree) that maps a column's values to the rows that have them, so the database can jump to matching rows instead of scanning the whole table. db.py:24, used by the query at app.py:22–24
🎯 Why we need it here: the only endpoint, GET /notes/{owner}, filters by owner. That column is exactly what the index sorts.
💥 What breaks without it: SQLite's plan changes from SEARCH notes USING INDEX idx_notes_owner to SCAN notes. We measured it on 1,000,000 notes: ~53 ms per lookup without the index vs ~0.02 ms with it, roughly 2,000× slower. Under load, that's the difference between snappy and timing out. (Trade-off: every insert also updates the index, so writes get slightly slower.)

The shelf is built and the key is on the front desk. The doors open… but who locks up at night? 🌙

❓ Predict it: you set NOTES_DB=/no/such/folder/notes.db and start the app. What happens, and after how long?
SQLite can't create a file in a folder that doesn't exist, so connect raises OperationalError. Dan waits 0.5 s, then 1.0 s, fails a 3rd time, and re-raises (db.py:14–16). The error travels up through init_db into lifespan, so the app fails to start after about 1.5 seconds and never serves a request.

No, not yet! The index already lives inside notes.db. Line 24 only says "create it if it doesn't exist". The slowdown hits only on a fresh database (a new machine, tests, a new environment), which makes it a sneaky bug.

📚 Glossary

  • Lifespan: setup before requests, cleanup after shutdown.
  • Retry with backoff: try again, waiting longer each time, then give up.
  • Database index: a sorted lookup that skips scanning every row.
